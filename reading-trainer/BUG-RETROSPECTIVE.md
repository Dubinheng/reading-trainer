本文记录新世纪 Reading Trainer 从 WorkBuddy 原型交接、登录页视觉重构、业务页面优化，到腾讯服务器主库、飞书同步副本、OAuth 与 DeepSeek 接入上线过程中遇到的主要问题、根因、修复方法和防复发规则。

## 一、项目背景与最终结论

项目最初是一个以单文件 HTML 为核心的浏览器应用。它已经具备学生、教师、管理员、邀请码、班级、文章、生词、错题、成绩和 AI 出题等功能，但视觉实现与 Illustrator 设计稿存在偏差，账号与学习数据也主要保存在浏览器中。

经过多轮修复，当前生产架构已经确定为：

- 腾讯服务器独立数据库 `reading_trainer.db` 是唯一主库。
- 飞书多维表格是脱敏、幂等、非破坏性的同步副本。
- 浏览器只保存页面生命周期内的临时 UI 状态，不持久化业务数据。
- 登录会话由服务器通过 HttpOnly、Secure、SameSite Cookie 管理。
- AI Key、飞书 Token 和管理员凭据只存在服务器私有配置中。
- 未经明确要求，不再修改已经验收的登录页视觉。

整体数据流：用户操作 → 正式网页 → API v2 → 腾讯服务器主库 → 飞书同步副本；AI 请求由腾讯服务器代理到模型服务商。

## 二、开发阶段

### 阶段 1：资料接收与基线核对

- 接收 WorkBuddy 工程、单文件 HTML、历史截图和报告。
- 对照 Illustrator 源稿、完整页面 PNG、用户视角 PNG、登录卡片参考图与 Logo 源图。
- 建立当前可维护工程目录，同时保留旧工程作为历史基线。

### 阶段 2：登录页视觉重构

- 使用设计底板和透明 Logo 重新搭建可交互登录表单。
- 反复校准卡片大小、白卡圆角、上下高度、左右边距、半透明旋转底片和桌面端比例。
- 增加背景粒子、渐变、进入动画和减少动态效果适配。

### 阶段 3：主页和练习流程优化

- 统一按钮为矩形圆角并增加阴影。
- 修正深色、浅色主题下按钮对比度。
- 调整学生练习设置、题量和题型比例入口。
- 清理重复、无效或不需要的操作按钮。

### 阶段 4：服务器化与飞书同步

- 增加 Flask API v2 和独立 SQLite 数据库。
- 将账号、邀请码、班级、收藏、生词、错题、成绩、文章库和设置迁移到服务器。
- 将飞书同步改为稳定业务键的幂等新增或更新，并保留飞书独有记录。
- 增加 OAuth 自动刷新、敏感字段过滤和旧浏览器数据安全迁移。

### 阶段 5：正式上线与回归保护

- 部署到腾讯服务器并通过正式 HTTPS 地址访问。
- 建立自动化后端测试、浏览器持久化契约检查和项目级 `AGENTS.md`。
- 将 GitHub 作为代码版本记录，将飞书作为业务数据同步副本和项目知识沉淀位置。

## 三、主要 Bug 与解决过程

### Bug 1：登录卡片比例与设计稿不一致

现象：登录卡片过大，白色表单上下过高，圆角或底板不能完整展示，中间内容比例与参考图不一致。

根因：最初直接按截图尺寸缩放，没有同时考虑底板透明边缘、浏览器视口高度、白卡实际可见区域和桌面端视觉重心。

修复：以参考图的视觉比例为准，使用视口高度约束卡片尺寸；分别校准底板、白卡和表单内容，而不是把整个卡片作为一张图片等比拉伸。

验证：在 469×676、1366×768、1440×900 和 1920×1080 等视口检查圆角、边距和无滚动溢出。

防复发：登录页已列为保护区域，未经用户明确要求不得顺手修改。

### Bug 2：白卡数学居中但视觉不居中

现象：CSS 左右边距相同，但白卡看起来仍偏向一侧。

根因：装饰底板的透明像素、图案密度和视觉重量并不对称，几何中心不等于视觉中心。

修复：根据实际截图像素分别设置左右可见边距，使白卡在最终渲染结果中居中。

经验：涉及透明 PNG 和不对称装饰时，应以最终可见轮廓测量，而不是只相信元素盒模型。

### Bug 3：半透明旋转矩形图层丢失

现象：设计稿白卡后方原有的半透明深绿色矩形消失，导致层次感和右上、左下露出效果不完整。

根因：重构时只保留了蓝绿色底板和白卡，没有拆出设计稿中独立的中间装饰层。

修复：恢复一整块半透明旋转矩形，并严格放在底板之上、白卡之下。

防复发：视觉重构前先建立“背景、底板、装饰层、白卡、表单内容”的层级清单。

### Bug 4：Logo 比例失真或出现白色背景

现象：Logo 在部分屏幕比例下被压缩、裁切，或因使用错误素材出现白底。

根因：原始 Logo PNG 带有较大的透明画布，直接按图片外框缩放会导致实际图形过小；某些导出图还带有不需要的背景。

修复：使用透明背景 Logo，并生成适合页头和登录页的紧凑裁切版本；保持 `object-fit` 和宽高比例。

### Bug 5：深色与浅色主题按钮对比度不足

现象：深色模式下按钮背景与页面背景融合，浅色模式下按钮颜色过浅，用户难以判断可点击区域。

根因：按钮颜色只围绕品牌渐变设计，没有分别验证两套主题的边框、填充、文字和悬停状态对比度。

修复：为深色和浅色主题分别设置按钮填充、边框、阴影和文字颜色；主操作按钮保留品牌渐变，次要按钮使用可识别的实体底色。

### Bug 6：业务数据错误地只保存在浏览器

现象：账号、成绩、错题、生词、文章和设置依赖 localStorage；换浏览器、清理缓存或换电脑后数据消失，也无法建立可靠的教师和管理员权限。

根因：早期原型为了快速演示，将 localStorage 当作数据库，并让前端直接管理身份和业务数据。

修复：建立 `/reading-trainer/api/v2`、独立 `reading_trainer.db`、密码哈希、服务端会话和按角色授权；浏览器只保留内存状态。

验证：在空浏览器中注册、保存收藏、刷新页面后仍能从服务器读取，并确认 localStorage 和 sessionStorage 中没有业务数据。

防复发：`scripts/check_persistence_contract.py` 会在重新加入浏览器持久化写入时直接失败。

### Bug 7：旧数据迁移可能先删后写

现象：如果迁移时先删除浏览器旧数据，再写服务器，网络失败会造成不可恢复的数据丢失。

根因：缺少明确的迁移事务顺序和成功确认。

修复：读取旧数据，与服务器数据取并集；只有服务器写入成功后才删除对应浏览器副本。冲突或失败时保留旧数据。

### Bug 8：Reading Trainer 可能误用原项目数据库

现象：服务器上已有其他业务的 `resumes.db`，如果新模块复用或覆盖该文件，会影响无关生产数据。

根因：多个应用共用同一 Flask 工程，但早期没有数据库边界保护。

修复：Reading Trainer 强制使用独立 `reading_trainer.db`，代码遇到 `resumes.db` 路径会拒绝启动；部署前后验证旧数据库未变化。

### Bug 9：飞书同步采用全量删除再重建

现象：早期同步逻辑读取远端后删除全部记录再重建；同步中断可能造成数据缺失，也会误删飞书独有记录。

根因：没有稳定业务键、幂等更新和远端差异分类。

修复：为账号、邀请码、班级和业务记录建立稳定业务键；同步只创建缺失记录或更新差异记录，永远不执行远端删除，并统计 `remote_only`。

验证：连续同步两次，第二次应为 0 创建、0 更新、0 删除。

### Bug 10：敏感信息可能进入前端或飞书

现象：历史方案中管理员密码、普通用户密码、AI Key 和飞书 Access Token 可能出现在源代码、本地存储或同步数据里。

根因：前端既承担界面，又承担认证、配置和第三方 API 调用。

修复：密码使用带盐哈希；会话使用 HttpOnly Cookie；AI 和飞书请求全部迁至服务器；同步采用严格敏感字段过滤；管理员账号不进入普通账号表和飞书。

### Bug 11：飞书 OAuth 短期 Token 到期后同步失败

现象：OAuth 授权最初成功，但 Access Token 到期后飞书同步失败，容易让人误以为每天都要重新授权。

根因：只保存了 Access Token，没有正确使用一次性的 Refresh Token，也没有原子替换新 Token。

修复：服务器在 Access Token 到期前自动刷新，并同时保存飞书返回的新 Access Token 和新 Refresh Token；私密 Token 文件权限为 600。

说明：正常情况下不需要每天授权；用户撤销授权、权限变化或长期授权周期结束时才需要重新授权。

### Bug 12：飞书同步由网页触发，失败后缺少后台重试

现象：每次服务器保存成功后网页会自动触发飞书同步，但如果保存后立即关闭网页或同步瞬间断网，飞书副本可能暂时落后。

根因：当前是事件触发的自动同步，还不是服务器常驻队列。

当前处理：服务器主库始终先保存，飞书失败不会导致业务数据丢失；下一次保存或管理员“立即同步”可补齐。

后续建议：增加服务器 Outbox、失败重试和定时对账任务，实现关闭网页后的最终一致性。

### Bug 13：本地 file 页面与正式网页混淆

现象：直接双击 HTML 后仍能看到界面，但相对 API 地址指向本地文件路径，容易出现服务器连接失败或误以为保存成功。

根因：视觉页面可以离线打开，但生产业务依赖同源 HTTPS API。

修复：在本地文件模式显示正式地址提示；README 明确要求正式业务使用 `https://kimdu.site/reading-trainer/`。

### Bug 14：DeepSeek 测试只测试旧 Key

现象：管理员在输入框粘贴新 Key 后直接点击“测试连接”，页面仍提示 `AI provider request failed`。

根因：旧按钮只调用测试接口，并不会先保存当前输入框内容；服务器实际测试的是原来保存的失效 Key。同时后端把 401、余额不足和限流都折叠成同一个通用错误。

修复：按钮改为“保存并测试”，先安全保存当前配置，再调用测试接口；后端将 400、401、402、403、404、429、超时和服务商故障映射为明确且不泄露上游响应的中文提示。

验证：无效 Key 会明确返回“API Key 无效或已撤销”；有效 Key 才显示连接成功。

### Bug 15：历史报告仍写着 localStorage，容易让后续 AI 回退

现象：代码已经服务器化，但旧 README 和过程报告仍描述“账号、成绩保存在 localStorage”，后续接手者可能按旧文档重新实现本地存储。

根因：架构升级后没有同步更新项目级约束和持续检查。

修复：更新 README 和数据持久化报告；增加 `AGENTS.md`，明确腾讯服务器主库、飞书同步副本和登录页保护规则；把数据契约纳入自动化测试。

## 四、当前测试与发布规则

每次修改至少执行：

1. `python3 scripts/check_persistence_contract.py`
2. `python3 -m pytest -q server/tests`
3. JavaScript 语法检查
4. 正式网页 API v2 健康检查
5. 涉及数据时验证“服务器保存 → 刷新读取 → 飞书幂等同步”
6. 涉及视觉时检查桌面主视口和浅色、深色主题

生产发布必须先备份服务器文件和 `reading_trainer.db`，再原子替换代码、重启 Flask、检查新进程和 HTTPS API。不得覆盖或删除 `resumes.db`。

## 五、最佳实践

- 数据先写服务器，成功后再同步飞书；失败时不得静默降级为本地保存。
- 飞书永远是脱敏副本，不承担密码认证，也不作为浏览器直连数据库。
- 所有第三方 Key、Token 和密码只进入服务器私有配置，不写文档、不进 Git。
- 所有同步操作使用稳定业务键，支持重复执行，默认不删除远端记录。
- UI 设计以实际视口截图验收；透明素材要测可见轮廓，不只看图片外框。
- “保存”和“测试”流程要符合用户操作顺序，避免测试旧配置。
- 错误信息既要可行动，又不能回显第三方响应体、密钥、内部路径或 Cookie。
- 架构变化必须同时更新 README、报告、测试和项目级 AI 规则。
